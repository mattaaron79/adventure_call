## Description
Drag a file chip somewhere, then expand it: the container header moves but the rows inside are drawn at the file's ORIGINAL laid-out position.

ROOT CAUSE
src/canvas/scene.ts reproject() applies overrides strictly per node -- 'for (const node of scene.nodes) placed.set(node.id, placedRect(node, overrides[node.id]))'. SceneNode has no notion of containment, so an override on a container does not translate the rows the layout phase placed inside it. The rows carry absolute world rects computed before the drag, and nothing shifts them. Same class of bug as tic-1d7c, one level down.

WORK
1. Give SceneNode a containment link (a parent id, set during assembly from the SpecNode.children tree in src/modes/types.ts -- the information already exists there and is discarded).
2. reproject() must translate a node by the accumulated offset of its ancestors as well as its own override, so moving a container carries its rows, its group box and its incident edges with it. Handle nesting to arbitrary depth (a class row inside a container), and make sure an override on both a parent and a child composes sensibly rather than double-counting.
3. Expansion happens AFTER the drag, so the row rects are produced by a fresh layout pass while the override is already in the store -- confirm the fix works in that order, not just when expanding first and dragging second. Both orders must land in the same place.
4. Dragging a row inside a container should keep behaving as it does today; this ticket is about containers carrying their contents, not about changing what is draggable.

EXIT: drag a collapsed file, expand it -- the rows appear inside the moved container; drag an expanded container -- rows, group box and edges travel with it; expanding then dragging and dragging then expanding agree.
