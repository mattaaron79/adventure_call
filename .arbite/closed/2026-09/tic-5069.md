## Description
Turn tic-b47a's per-call-site breadcrumbs into the per-edge vocabulary the user asked for: does A always call B, sometimes call B, or both.

An edge from A to B aggregates every call site in A that targets B. From their breadcrumbs derive:
- `unguarded` -- every site sits at guard_depth 0
- `guarded` -- every site sits inside a guard
- `mixed` -- both, which is genuinely common and genuinely worth seeing
- `looped` -- some site sits inside a for/while, so the edge can fire N times
- `error-path` -- every site sits in an except or finally block
- `type-checking-only` -- every site is under `if TYPE_CHECKING`, i.e. not runtime flow at all

Then roll the edges up to node tags: a function every one of whose incoming edges is error-path is an error handler, whatever it is named; one only ever called inside loops is hot.

Naming, again and non-negotiably: `unguarded`, never "unconditional" or "always". guard_depth 0 does not mean the call happens -- an early return or raise above it kills it, and the caller may itself be conditional. The word choice is the difference between the mode informing a reader and misleading one. tic-3a20 is where a true "unavoidable" would come from.

Carry the tags on SpecEdge.data, which exists precisely for mode-private per-edge payload (added in tic-56b2 for exactly this shape of problem) -- do not encode them in SpecEdge.kind, or the cross-mode machinery keyed on kind (selection highlighting, marching ants) will stop recognising these as call edges.

Verification: unit tests for each tag and each aggregation case, especially mixed, and an edge whose sites disagree about loop membership. Report the tag distribution across the real ../carnot export in the notes -- if 95% of edges come out `unguarded`, the tag is not earning its ink and we should know that before tic-23eb spends visual budget on it. npm run test, tsc -b.

## Where the tags live

Edge tags ride on `SpecEdge.data`, per the ticket, never on `SpecEdge.kind` --
the cross-mode machinery keys selection highlighting and marching ants on a
`call` kind, and encoding a tag there would quietly stop these being
recognised as call edges. There is a test that asserts every scene edge still
has kind `call`.

Node tags go in the chip's identity clause, the same slot as the framework
role, because they are the same kind of claim (what part does this play) and
both are short and rare enough not to crowd it:

  _dispatch — playground · hot · reaches 45 · 2/7 sites resolved
  done      — tui · error handler · reaches 1 · 1/2 sites resolved

So this ticket consumes its own data rather than leaving another unread
dataset behind; tic-23eb still owns the edge STYLING.

## Two things found while building

1. BREADCRUMBS HAVE TO POOL, NOT FIRST-WINS. tic-171f rewrote
   `callEdgesBetween` to collapse several call-graph edges onto one drawn
   line. A condensed knot means one line can carry two functions' calls to the
   same target, and if one is guarded and the other is not, `mixed` is the
   true answer for the line. Tagging each edge and picking one would report a
   fact about a call the reader cannot see. (My first patch to that function
   silently no-op'd against 171f's rewrite, because I had not put an assert on
   the replacement -- caught by the compiler, but only by luck.)

2. `hot` MEANT TWO DIFFERENT THINGS. The docstring said "every incoming call
   SITE is inside a loop"; the code rolled up from `looped`, which is true
   when SOME site is. On carnot that was the difference between 83 hot
   functions and 97, and the extra 14 are simply not hot. Added `allLooped` to
   EdgeTags -- every site -- and the roll-up uses that, so doc and code agree
   and the number matches an independent measurement.

   The first mutation run did NOT catch this: the fixture only had edges where
   `looped` and `allLooped` agreed, so swapping them passed 20 of 20 tests.
   Added a case where they differ; the mutation now fails.
